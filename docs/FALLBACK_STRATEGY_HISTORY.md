# Сравнение fallback 0.2.0/0.2.2 и локального r44

2026-11-26. Запрос пользователя — исследовать прежнюю стратегию, а не менять её или устанавливать новый комплект. Live подключения, конфиги, restart и публикация в этом сравнении не выполнялись. Проверка статическая по локальным Git tags и текущей серии; реальная частота переключений старых устройств не воспроизводилась.

## Подтверждённая база

`git show 0.2.0:core/UPSTREAM`: core package r14; `git show 0.2.2:core/UPSTREAM`: r22. Pinned upstream commit один. `git rev-parse TAG:core/patches/0001-stable-fallback.patch` для обоих tags и HEAD возвращает `f4912ffb06c7cc992f1db2cb719eb85d4d528efa`. Содержимое patch0001 побайтно одинаково также с текущим рабочим файлом. Между этими двумя app tags стратегия stable fallback не менялась.

Python subprocess `git show` + извлечение `fallback_stability(section, value)` из `config/connections.uc`: обе функции побайтно равны текущей. Defaults: stable=true, Cloudflare confirm204, retry3s, recovery60s, return3successes. Текущие конкретные UCI overrides пользователя не восстанавливались из tags; старые реальные таймеры не объявляются известными. Defaults health interval5m, timeout5s не объясняют сами по себе новый критерий отказа.

## Главное изменение r42

Раньше при отказе primary результат confirmation **замещал** err: `delay, at, err = coordinator.Check(confirmURL, ...)`. При Google timeout/Cloudflare ok конечный err=nil: h.alive=true, failed_checks не увеличивается, suspect/confirmed Warn и проверка резерва по этому событию не возникают. Это критерий «достаточно одной успешной HTTPS-проверки». При успехе primary второй URL вообще не нужен.

Patch0042 оставляет err от primary, confirmation хранит отдельно. Google timeout/Cloudflare ok теперь увеличивает failed_checks, создаёт suspect, после повторного отказа primary — confirmed failure. Резерв тоже должен пройти primary; если он не проходит, r42/r44 сохраняют выбранного участника даже при all-unhealthy. Это отличается от прежнего «успех любого URL» и объясняет рост тревог/счётчиков при работающих других сервисах. Возможность роста реальных переключений следует из изменения критерия, но историческая частота аппаратно не измерена.

Второе изменение0042: при частичном отказе отключён veto по fresh data (`!partialFailures[...]`). Старый veto уже был узким: только полученные данные на **новом TCP-соединении, созданном в текущем раунде**, с той же outbound/target identity. Само непрерывное старое видео не доказывало здоровье нового подключения ни в старой, ни в текущей версии. Поэтому утверждать «старая версия вообще никогда не переключалась во время видео» по коду нельзя.

То есть старое поведение не было просто «все сообщения спрятаны»: health Warn уже существовали. При частичном Google отказе они не появлялись из-за **иной оценки доступности**. Глобальная классификация обычных connection errors в0.2.0/0.2.2 ещё не содержала поздних0026+ улучшений; откат всей серии вернул бы нежелательный шум и убрал другие исправления.

## Вывод и границы

Подтверждается конкретная причина большей чувствительности после r42: primary-service failure стал приравниваться к unhealthy даже при успешном независимом HTTPS. Это не просто изменение уровня журнала и не ускоренный таймер по умолчанию. Разумное направление следующего изменения — отдельно оценивать общую доступность туннеля и частичный отказ primary; последний не маркировать полным outage. Возвращать всю старую версию или автоматически ослаблять TLS/data evidence не требуется. Политика перехода при частичной недоступности конкретного сервиса должна быть отдельным явным решением; в этой задаче production не менялся.
