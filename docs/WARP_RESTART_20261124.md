# WARP: повторный restart-тест 2026-11-24

Установлено: **0.2.5/core r34**, исходники pinned UPSTREAM + 34 patches. После сообщения пользователя о новом отказе пользователь прямо разрешил проверять WARP перезапусками KabanMax. Старое правило без ручных restart на этот тест отменено его новым указанием. Настройки, профили и уровни журнала не менялись.

## Метод

Два автономных ограниченных shell запуска на самом роутере: `/root/kabanmax-warp-restart-test-20261124/run.sh` и `run-2.sh`, через `setsid sh SCRIPT </dev/null >/dev/null 2>&1 &`. Это диагностические scripts, не альтернативный deployment installer. Каждый выполняет штатный `/etc/init.d/kabanmax restart`, ждёт 8s после возврата команды и последовательно запрашивает authenticated `GET /proxies/OUTBOUND/delay?timeout=8000&url=https%3A%2F%2Fwww.youtube.com%2Fgenerate_204` для двух отдельных WARP и общего WARP fallback. Перед restart — baseline. При отказе — повтор через 25s, затем ещё через 25s, без нового restart; серия останавливается для сохранения состояния. Trap обеспечивает start, если служба неожиданно останется остановленной. Отдельных stop/kill sing-box нет.

В результаты попадают только время, задержка/ошибка, PID и UDP ports/counters; секреты не выводятся. Debug не включался. Дополнительный read-only AF_PACKET helper второго теста работает 12s, `GOMEMLIMIT=8MiB`, считает тип/длину пакетов без payload/keys. Скрипты завершились, фонового restart-таймера не осталось. Планировалось до трёх циклов; фактически выполнены **два**, каждый остановлен на воспроизведённом отказе.

Обе попытки воспроизвели отказ второго профиля после restart при успешном baseline. В первом цикле новый UDP source port получил ответы, WARP2 восстановился к следующему измерению через 26s после Timeout. Во втором новые ports оставались UNREPLIED более минуты, затем профиль также восстановился без ещё одного restart. Второй core PID `6952` сохранился до итоговой пробы, служба running. Это не два стабильных успешных старта.

Пакетный счётчик второго цикла подтвердил выход реального 148-byte handshake-init второго профиля на WAN; обратных пакетов для него в окне нет. Первый профиль получал encrypted transport. Изменение source port само по себе не гарантировало быстрый ответ. Этот результат не устанавливает виновником провайдера/Cloudflare/NAT и не доказывает совпадение identity; ранее выполненный read-only API/cache comparison не обнаружил key mismatch.

## Вывод и ограничения

**Исходный WARP startup/reload баг остаётся открытым.** r32 включает существующее self-heal и подтверждённо помогает восстановлению, но не обеспечивает работоспособность обоих профилей сразу после restart. Один успешный recovery/HTTPS smoke не является достаточной приёмкой исправления. Нужна дальнейшая диагностика первого неотвечающего UDP flow и recovery, с повторяемыми restart-пробами.

Чтение pinned кода проверило: Amnezia IPC формируется до установки peers; egress pool имеет отдельный RX и закрывается/пересоздаётся при bind update. Само чтение не доказало в них гонку. Неподтверждённые гипотезы не превращены в новые WARP patches.

Независимое изменение Pending по новому требованию пользователя начато, но прервано сообщением о WARP: draft `0035-stable-pending-check-results.patch` и обновлённая regression не установлены и не объявляются проверенными. Требование: один успешный результат хранится до удаления/применения/исключения, без протухания, автоматических повторов и новой кнопки. На устройстве всё ещё r34 с предыдущим поведением. Новых пакетов или публикаций в этом restart-тесте нет.
