## Продолжение 2026-11-24: подтверждённый UDP outage

После успешного штатного обновления 0.2.4/r31: WARP1 HTTPS timeout, WARP2 30 мс; повторно WARP1 timeout, WARP2 41 мс, fallback выбрал второй. Без перезапусков прочитан `/proc/net/nf_conntrack` (вывод ограничен counters/ports, WAN/client addresses не публиковались): первый peer UDP 4500 — 259 outgoing packets / 61386 bytes и **0 replies**, UNREPLIED; второй UDP 2408 — 517 outgoing / 324 reply packets, ASSURED. Это локализует отсутствие ответов peer UDP, но не устанавливает причиной провайдера, Cloudflare, ключи или NAT.

Пользователь уточнил: каждый профиль создавался заново и нигде больше не используется; оба профиля могут отказывать, изменение «Запрашивать WARP через секцию» восстанавливает работу. Совпадение ключей между двумя текущими профилями уже исключено. Гипотеза повторного использования на другом устройстве не подтверждена и больше не должна подменять диагностику наблюдаемого reload-сбоя.

По прочитанному pinned `protocol/warp/endpoint.go`: при заданных id/token/private_key `createConfig` читает существующий профиль, не создаёт новый ключ; cached config используется при валидной identity. `warpCacheKey` включает tag/id/token/private_key/license, но не API detour. Reload создаёт новый runtime endpoint/UDP socket, а не обязан регистрировать новый Cloudflare профиль. Поэтому эффект checkbox прежде всего совместим с пересозданием транспорта; роль API/cache и гонку parallel bootstrap нужно доказать отдельным тестом, а не предполагать.

Linux direct WARP использует StdNetBind. В vendored wireguard-go уже существует give-up recovery, но transport не вызывал `SetGiveUpRebind`: восстановление повторно открывало прежний UDP порт. `SetSinglePeerMode` на Linux — no-op, `ClearSrc` не меняет порт. Patch `0032-wireguard-fresh-port-recovery.patch` включает существующую смену порта только для single-peer клиента без явно заданного listen_port. Server/multi-peer/pinned-port identity сохраняется; новый watchdog и регистрация профиля не добавляются.

Read-only диагностика 2026-11-24: первый flow накопил 9268 исходящих/0 ответов на одном source port. Bounded AF_PACKET helper увидел настоящие 148-byte handshake-init на WAN, не только обфускационные datagrams. ## Подтверждённый дефект

В закреплённом upstream `route.NetworkManager.ResetNetwork` уведомляет только endpoints с `adapter.InterfaceUpdateListener`. Вложенный WireGuard реализует этот интерфейс и пересоздаёт UDP bind, но WARP wrapper его не реализовывал. Поэтому WARP пропускал восстановление транспорта после network reset/interface update. Пересоздание всего endpoint при reload могло временно восстанавливать связь.

Patch `0029-warp-network-reset.patch` добавляет интерфейс wrapper и передаёт исходный context вложенному транспорту. Указатель читается под RLock; вызов выполняется после освобождения lock. До завершения асинхронной регистрации уведомление не ждёт профиль. Закрытие/отмену и синхронизацию bind продолжает обеспечивать WireGuard. Сетевые ограничения, API detour и fallback evidence не меняются.

## Диагностика устройства

2026-11-23 пользователь разрешил диагностическое подключение к локальному роутеру. Устройство: OpenWrt 25.12.5, ARM64, установленное ядро `1.14.4-r22`.
