## Обычный HTTPS без nonce — №04Б-ФИНАЛ

Существующие две галочки сохранены: opt-in включает наблюдения/проверки/предложения, auto-apply отдельно и по умолчанию выключен. Пустое поле настроек теперь означает **web**: TCP/443, GET `/`, статус 200, исходное доверенное имя потока. Старый JSON без `mode` по-прежнему означает **strict**, его семантика не меняется. Явная web-настройка:

```json
{"mode":"web","path":"/","port":443,"status":200}
```

Необязательный `domain` сужает проверку одним именем; без него проверяются доверенные FQDN из реальных соединений этой Zapret2-секции. `prefix` задаёт ожидаемое начало содержимого. Никогда не подставлять ручное имя к чужому IP: backend передаёт Query существующего core candidate, а web core guard требует совпадающее наблюдение TCP-потока (source/port/inbound/section/domain/IP). Origin section ID и routing mark возвращаются в событии.

Ordinary verifier использует тот же конкретный outbound, pinned real IP, SNI/Host и TLS chain/hostname verification, новый transport и cache-busting query в каждой попытке. Он не требует отражать nonce. GET ограничен 4 KiB body sample, заголовки ≤8 KiB, попытка ≤2 секунд; redirects не выполняются. Допустимый ответ: заданный статус 2xx (по умолчанию 200), HTML/text/JSON, ≥32 непустых байт и configured prefix, если задан. Большая страница проверяется по ограниченному образцу, полное содержимое не сохраняется. Возвращаются hostname/path/port/method, outbound/mark, dial IP/peer, TLS/HTTP status, content type и размер образца.

Redirect, 401, 403, 429, 405, 5xx, известные captcha/anti-bot markers, cached Age, неожиданное сжатие/тип/содержимое и неверный сертификат — отдельные inconclusive outcomes, не подтверждение работоспособного приложения и не основание переключения. HEAD не используется: 405 при GET также не считается блокировкой. Успешный TLS без пригодного тела не достаточен. Body timeout/EOF после заголовков — транспортный сигнал, не «приложение исправно» и не доказательство DPI.

Классификация evidence:

| Evidence | Условие | Разрешённое действие |
| --- | --- | --- |
| `healthy` | Две свежие попытки исходного пути соответствуют режимному контракту | Сохранить маршрут; альтернативы не проверять |
| `suspected_failure` | Два транспортных сбоя исходного пути в одном bounded job | Диагностика; это не доказательство блокировки |
| `alternative_reachable` | После этих двух сбоев две попытки разрешённой альтернативы отвечают по web-контракту на **том же IP/port/hostname/path**, свежий DNS не изменился | Предложение с ручным Apply только при узком scope/TTL/guard; **никогда auto-apply** |
| `verified_for_apply` | Только прежний strict nonce-контракт: 2 явных свежих отказа исходного + 2 подтверждённых успеха альтернативы | Auto-apply лишь при второй галочке, иначе предложение |

Успех альтернативы исключает полный сетевой отказ в момент этой проверки, но не доказывает отсутствие кратковременной аварии, серверной селекции, балансировки или незамеченного anti-bot. Две обычные HTML-страницы не дают строгой nonce-свежести и не доказывают доступность остальных функций сайта. Поэтому даже включённый auto-apply не применяется к web. Один сбой, смешанный результат или глобальная недоступность не дают предложения с правом применения. Поле `apply_allowed` устанавливается только сервером; UI дополнительно проверяет domain_known и срок. Apply не обходит policy, DNS и точную область.

Для web **нет перебора DNS-адресов**: проверяется только IP реального потока. Hook результата dial связывает `conn.RemoteAddr` с тем же core event и уже известным из его Destination.Fqdn именем. Если при нескольких адресах все dials не удались и нельзя выделить конкретный адрес, событие остаётся видимым с `actual_destination_ip_unknown`; угадывать IP или проверять все A/AAAA запрещено. При единственном адресе он известен из metadata уже при ошибке. IP из raw log без источника остаётся unattributed.

IP-only от атрибутированного TCP-потока допускает две ограниченные TCP dial-попытки по каждому разрешённому пути после guards, без HTTPS/SNI с выдуманным именем. Результат — `identity_unknown` / `transport_diagnostic`: видны транспортные факты, но нет ни application success, ни Apply, ни lease. При неизвестном protocol-dependent earlier rule диагностика также fail closed. UDP видим, но не проверяется TCP/HTTPS.

Для защиты соседних A/AAAA воспроизведён и исправлен дефект старого matching: **lease используется только когда исходная маршрутизация уже оставила единственный точный DestinationAddress**. Lease не выбирает проверенный IP из смешанного списка за первоначальный dialer. При неоднозначном имени ручная lease может остаться неприменимой к такому потоку; другие адреса/соединения остаются на Zapret2. Пробы одного IP при этом доступны, но никакого переноса всего домена нет.

Web recheck через 5 минут не продлевает разрешение незаметно: прежняя lease снимается, новый результат требует ручного подтверждения. Строго подтверждённое продление разрешено только для прежней цели; выбор другой цели без права auto-apply не выполняется. TTL, Delete/Clear/Reset/Stop, suppression и отмена generation остаются прежними.

## Строгий nonce-режим: что считается доказанным

`GET /kabanmax/auto` читает состояние; аутентифицированный `POST` выполняет конечные операции `probe/apply/delete/clear/reset/disable`. Запись дополнительно требует непустого секрета Clash API. LuCI использует отдельный write-RPC `auto_action`; общий read/exec не даёт права записи. Длительная проверка работает в дочернем CLI worker, не блокируя rpcd event loop.

Проверка создаёт новый HTTPS transport для каждой попытки, вызывает конкретный outbound с закреплённым реальным IP, сохраняет домен в SNI/Host и проверяет сертификат штатным trust store. Нет `/delay`, URLTest, изменения selector или использования health history. Запрос содержит случайный nonce в query и `X-Kabanmax-Probe`; успешный ответ обязан вернуть этот же заголовок и точное тело `prefix + nonce`, ожидаемый статус 2xx, без признаков кешированного Age. Redirect не принимается. Одна удачная попытка недостаточна: нужны две независимые.

Пример **синтетического** контракта секции:

```json
{"mode":"strict","domain":"control.example","path":"/health","port":443,"status":200,"prefix":"ok:","failure_status":451,"failure_prefix":"fail:"}
```

Отказ исходного Zapret2 доказан только двумя свежими TLS-ответами, удовлетворяющими явному `failure_status/failure_prefix` контракту. Тайм-аут, TLS-ошибка, произвольный 200/403 и чужое содержимое дают `inconclusive`, не разрешение Direct. Если исходный маршрут подтверждён, менять его нельзя. Если исходный отказ не доказан либо его проверка запрещена, альтернативы не пробуются. Контрольный endpoint доказывает только заданный endpoint/путь, не работоспособность целого приложения или всех сайтов на этом IP.

Разрешения независимы: исходный Zapret2, Direct (по умолчанию запрещён), конкретный native WARP. Не выбранный WARP не проверяется. WARP не подменяется VPN/VPS/URLTest/Fallback. После подтверждённого отказа исходного маршрута проверяется Direct, затем разрешённый WARP. При отсутствии доказанного результата исходная маршрутизация сохраняется. Решение хранится на сервере и применяется по одноразовому ID с повторной проверкой политики/DNS/срока; клиент не передаёт «успех».

## Порядок и область действия

Каждое пользовательское соединение сначала проходит прежний настоящий route matcher r10. Только если реально выбран opted-in Zapret2 outbound с ожидаемой routing mark, рассматривается автоматическая lease. Поэтому предшествующие Block, Bypass, Connection, ограничения устройств и ручные правила сохраняют first-match. Правило Block после Zapret2 имеет прежнюю семантику и не становится глобальным запретом. Автоматизация не вставляет глобальный IP-Bypass перед списком пользователя.

Lease требует одновременно: исходный outbound, точный доверенный домен `Destination.Fqdn`, один разрешённый реальный IP из исходной выборки, source IP, inbound, TCP и destination port. Дополнительно проверяются global excluded devices/System. Имя из reverse DNS, совпадение CDN-IP или произвольное `metadata.Domain` не создают доверенную принадлежность. FakeIP поддерживается, когда ядро само восстановило исходный FQDN из своей карты. IP literal с неподтверждённым именем остаётся наблюдением `identity_unknown`.

Probe повторно вызывает штатный matcher с TLS/TCP, IP version и доступными параметрами исходного соединения, включая source port. Если предшествующему правилу нужны недоступные process/interface/WiFi или другие клиентские признаки, результат неизвестен и проба не разрешается. Opaque SRS и неизвестные контексты не превращаются в положительный match.

DNS запрашивается заново через явный `dns-server` с отключённым cache/optimistic cache. Проверяются exact Answer owner, qtype A/AAAA, IN class, min TTL, неизменность полного набора перед/после проверки и перед применением. Максимум четыре адреса, точный проверяемый IP, отказ при изменении набора, FakeIP или недопустимом адресе. Сейчас CNAME-ответы намеренно дают неопределённость: полная проверка цепочки не реализована. Изменение DNS или исчезновение целевого outbound снимает lease.

## Наблюдения, срок и откат

Core наблюдает реальные соединения исходных Zapret2, включая IP без hostname и UDP. Ошибка или отсутствие входящих данных более 15 секунд после отправки данных — повод проверить приложение, не доказательство его отказа. Прогресс учитывается отдельно по соединению; старая активная сессия не маскирует новый сбой. UDP сохраняется в диагностике, но HTTPS-проверка к нему не применяется.

Backend также показывает IP-first ошибки журнала и no-progress из `/connections`, но не приписывает их Zapret2 по названию `direct-out`. Неатрибутированные записи видимы, изменения маршрута по ним запрещены. Никакого сопоставления имени с IP по соседней строке лога или текущему DNS.

Один probe job за раз; не более 12 IP-проверок за час, cooldown области 5 минут. На каждый IP максимум 6 HTTPS-запросов (2 × 3 маршрута), до 24 на пакет из четырёх IP, общий предел 60 секунд и 2 секунды на попытку. Sweep раз в 5 секунд выбирает не более одного задания; одна и та же обработанная запись не запускает вечный цикл. RAM ограничена: 128 событий, 100 решений/leases/истории, 256 cooldown; read view сокращён до 64 событий, 20 решений и 30 записей истории. Backend хранит максимум 128 неатрибутированных наблюдений за час.

Lease действует до min(DNS TTL, 15 минут), отсчитываемого от начала проверки. Для длительных leases повторная проверка через 5 минут; неудачная или недоступная повторная проверка возвращает исходный маршрут. Ошибка реально использовавшего альтернативу соединения сразу снимает только его собственную lease; позднее закрытие старого соединения не отменяет заменившую её lease. Новые соединения после отмены используют прежний matcher. Уже открытые пользовательские TCP-соединения принудительно не мигрируют.

Leases и доказательства находятся в RAM текущего Box; restart/reboot/JSON reload не восстанавливает старые разрешения Direct. После нового запуска нужна новая проверка. Save & Apply может прервать TCP так же, как обычный JSON reload; старый fallback №03 не менялся.

Удаление/очистка отменяет runtime leases и сохраняет suppression с owner `auto-routing` в отдельном атомарном `/etc/kabanmax/auto-routing-suppression.json`. Ключ содержит стабильный UCI ID исходной секции и узкую область, не её отображаемое имя. Файл отделён от пользовательского UCI, чтобы не перезаписывать staged ручные настройки; максимум 1024 записи, повреждение/чужое ownership — fail closed. Сброс suppression разрешает новый подбор, но не возвращает старый маршрут без проверки. Runtime stop действует до нового Apply; для постоянного выключения снять opt-in и Save & Apply. Операции runtime требуют работающего r11 API, включая reset; при выключенном сервисе ручной офлайн-редактор suppression не предоставлен.

Clear/delete/disable отменяют выполняющийся job и меняют generation. Устаревший результат не может снова примениться. Отмена по ID затрагивает только owner автоматики; ручные списки, порядок секций и nft rules не редактируются.

## LuCI

В секции Zapret2 есть opt-in, отдельные разрешения проб, автоматическое применение (по умолчанию выключено), HTTPS-контракт, выбор конкретного WARP и необязательная секция Bypass для отображения Direct. После изменения параметров нужен обычный Save & Apply. Вкладка показывает кандидатов с IP без домена, результаты, предложения, активные перенаправления и историю; доступны Check, Apply, Delete, Clear, Reset suppression и Stop.

В целевых Bypass/WARP показан виртуальный список «Добавлено автоматически» с возвратной информацией об исходной секции. Отображение в Bypass не превращает lease в обычное ручное правило и не меняет порядок. Ручных Add/Edit для автоматических IP нет. Подробности содержат evidence; неизвестность и применённый результат разделены. Read-only прогноз №04 остаётся отдельным объяснением конфигурации, не active verifier.

## Защита инфраструктуры и честные ограничения

RU blackhole, существующий nft/mark и маршруты VPS не меняются. Probe не использует VPS outbound; backend отказывается включать режим при основном DNS через VPS/opaque/Fallback/URLTest, не переписывая DNS. Из конфигурации собираются защищённые IP/имена инфраструктуры, включая WARP service endpoints; их DNS-алиасы также исключаются. Непрозрачные VMess/URI и динамические подписки, для которых невозможно собрать endpoint inventory, запрещают opt-in. Российские TLD, private/loopback/link-local/multicast/FakeIP назначения блокируются. Это не универсальная классификация географии по IP; сохранение RU blackhole обязательно и после установки.

API доказывает конкретный dialer/mark и проверенный TLS peer; nonce-свежесть приложения доказывает только strict режим. В web доказывается ограниченный HTTPS-ответ, без равной гарантии свежести. `physical_egress_verified` остаётся **false**. API не доказывает публичный адрес выхода за чужим policy routing, NFQUEUE на реальном роутере или реальную работу WireGuard WARP у провайдера. Эти сценарии требуют отдельной аппаратной приёмки. В тестах WARP — контролируемый транспортный адаптер; реальные WARP/VPS/российские сервисы не вызывались. Не выдавать обычные проверки за универсальную диагностику игр/медиа/UDP/полной функциональности произвольных приложений; для строгого автоматического решения по-прежнему нужен контракт приложения.
