# ТЗ №04: безопасная диагностика и автоподбор маршрута

## Одобренное продолжение №04Б

Пользователь разрешил минимальное расширение core поверх r10 и отдельную тестовую сборку: недостаточность `/delay` не является конечным препятствием. Предпочтение — runtime lease после штатного first-match Zapret2, exact domain AND real IP AND device/port, с TTL в ядре. Источником доверенного имени считается исходный Destination.Fqdn / подтверждённый FakeIP-контекст; общий reverse DNS/cache не авторизует lease. Новый Box не восстанавливает непроверенные исключения.

Обнаружение IP-first обязательно: log IPv4/IPv6 и no-progress с пустым host сохраняются с destination/source/port/network/timestamp/repetition и доказательством исходной Zapret2-секции либо unattributed. Неизвестный домен показывается как «Не установлен», unknown identity остаётся inconclusive. UDP показывается отдельно, не проверяется HTTPS/TCP контрактом. Опциональная корреляция DNS не выдаётся за доказательство принадлежности соединения.

Порядок реализации: scoped core semantics → independent probe API → backend/IP-first/suppression → виртуальные автоматические списки внутри пользовательских секций → регрессии собранного core. Прежний read-only checker сохраняется. Детали и reference audit — [план №04Б](../plans/2026-11-15-auto-routing-04b.md).

Статус: одобрено пользователем с дополнениями ниже; выполнение одним агентом без повторного согласования. Основание — приложенное `KABANMAX_CODEX_04_AUTO_ROUTING_DIAGNOSTICS.md`, запрос и последующее подтверждение пользователя. Решения ниже, если не заданы ТЗ, предложены исполнителем.

## Уточнения пользователя после согласования

Автоматика включается отдельно для каждой Zapret2-секции и рассматривает только IP, действительно попавшие в неё по текущему порядку правил. Рабочая исходная стратегия ничего не меняет. Timeout, HTTP 403 и разрыв TCP не являются подтверждённой проблемой приложения. Допустим явный запуск с проверяемым контрольным ресурсом. Если альтернативы нет, исходная конфигурация сохраняется. Connection, Bypass и Block не являются источниками автоподбора.

Block оценивается по реальному приоритету и source/port scope: если это первое совпадение, никаких активных проб или перенаправлений. Block ниже уже совпавшего Zapret2 не меняет прогноз задним числом. Неопределённость в более раннем правиле останавливает автоматизацию. Пробы каждого из Zapret2, Direct и WARP разрешаются независимо; запрет Direct сам по себе не запрещает WARP. Все запрещены — `blocked_by_policy`.

В исходной Zapret2-секции нужен блок «Автоматическая маршрутизация»: opt-in, статус, счётчик IP, предложения, активные правила, история, отмена одной записи и очистка секции. В пользовательских Bypass/WARP-секциях — отдельный список «Добавлено автоматически». Поля: точный IP, домен, исходная секция, целевой маршрут, причина, время создания/expiry, статус и детали диагностики. Managed-секции отображаются через эти списки, не как ручные записи.

Автоматические списки только для чтения и удаления: никаких ручных add/edit/pin. Создаёт записи только backend после проверки. Удаление снимает реальное правило и сохраняет suppression по IP + исходной секции + domain/source/port scope. Очистка аналогична удалению всех записей секции. Suppression переживает reboot и Save & Apply; отдельный сброс снова разрешает подбор. Ручные списки независимы и никогда не изменяются автоматикой. Записи содержат ID, owner `auto-routing`, source section, route/profile, /32 или /128, domain/device/port, evidence, created/expiry, status и decision ID.

Если существующая архитектура не позволяет обеспечить точность и безопасность, пользователь явно разрешил реализовать безопасную часть с фиксацией препятствия. Нельзя объявлять mock transport реальным доказательством или создавать работающую кнопку применения при неподдерживаемой проверке.

## Цель и границы

Один общий backend-движок объясняет маршрут назначения и обслуживает ограниченный подбор Zapret2 → разрешённый Direct → WARP. Диагностика ничего не меняет. Применение включается явно для выбранной секции/назначения; по умолчанию выключено. Dry-run не записывает UCI и не переключает selector.

Работа в текущем dirty tree одним агентом. Без коммитов, публикации, оборудования, реальных российских сервисов/VPS. Существующие задачи №01–03, пять patches, r10, no-op Save, DNS/FakeIP и Fallback не переделываются без воспроизведённой регрессии. RU blackhole не меняется.

## Подходы

1. Постоянно перемещать адреса между исходными секциями. Отклонено: трудно отделить ручное изменение от автоматического и безопасно вернуть исходные списки.
2. Собственный nft overlay в обход UCI. Отклонено: ещё один источник политики, риск расхождения с DNS, устройствами и sing-box.
3. Общая диагностика и принадлежащие ей обычные UCI-секции с точными адресами и метаданными. Предлагается этот вариант: исходные секции сохраняются; generator, validator, nft и штатный lifecycle остаются механизмами применения. Автосекция располагается непосредственно перед исходной Zapret2-секцией, после всех более ранних ручных правил. При изменении политики выполняется повторная проверка допустимости, а не слепое восстановление snapshot.

## Контракт диагностики

Ввод: одно имя домена или IP, порт (по умолчанию 443), необязательный источник LAN. URL для активной проверки — только явно выбранный безопасный HTTPS-ресурс; без credentials, произвольных схем и автоматических redirect. IP literal требует явно настроенной TLS identity/ожидаемого ответа для подтверждения работоспособности приложения.

Вывод разделяет:

- `predicted`: первая совпавшая секция, порядок, source/port scope, причина, исключения и доступные данные DNS;
- `observed`: активный selector/leaf и свежие факты runtime, если доступны;
- `verified`: конкретный HTTPS-запрос через конкретный outbound к конкретному реальному IP и время проверки.

Проверка router-origin outbound не доказывает фактический путь пакетов LAN-клиента через nft/PBR. Отсутствующий источник при device-зависимых правилах даёт неопределённость, а не глобальную рекомендацию.

Прогноз строится по существующим парсерам `config.rule`, модели `config.connections` и порядку runtime-секций; сопоставление проверяется fixtures с результатом generator. Неизвестные SRS, неизвестный protocol/sniff, missing provider и неполные runtime-данные дают `unknown`, блокирующий автоматическое применение. Не изображать второй упрощённый matcher точной копией core.

## Policy guard до DNS и до каждой пробы

Защищённое назначение, VPN endpoint, ручное Block/VPN-правило, исключённое устройство, неясная политика или конфликт запрещают автоматическое исключение. Обычный final Direct не считается согласием на Direct-пробу. Нужны явный opt-in и разрешение Direct для выбранного назначения. Zapret2 также имеет прямой egress, поэтому тот же запрет применяется к его активным пробам.

Endpoint guard учитывает настроенные IP/имена инфраструктуры и свежие разрешённые адреса; неизвестный endpoint/alias закрывает возможность автоматизации. Для DNS-ответа каждый A/AAAA проверяется отдельно. Новые IP после DNS не наследуют разрешение старых. Защитный denylist имеет приоритет над allowlist.

WARP разрешён только как явно выбранный и готовый профиль без detour через VPS/произвольный VPN. Каскады и неизвестный фактический egress не используются. Никаких проб российских сервисов с VPS. В этой задаче все назначения и транспорты синтетические, тестовый контейнер без внешней сети.

## Доказательство успеха

TCP dial, RTT, handshake без ответа приложения, произвольный HTTP 200/403 и wildcard status не подтверждают маршрут. Для успеха нужны две независимые новые попытки: проверенный TLS hostname и цепочка сертификатов, точный ожидаемый HTTP status, настроенный признак ожидаемого ответа, подтверждённый remote IP, нужный outbound и отсутствие redirect/cache-ответа. Ошибка или недостающий факт дают `failed` либо `inconclusive`, не `success`.

Запрос не использует browser/proxy cache; ограничены время, размер ответа и количество данных. Nonce допускается лишь в согласованном контракте контрольного endpoint: случайный URL сам по себе не доказывает отсутствие CDN cache. Ответ без достаточного признака свежести остаётся непригодным для автоматического сохранения.

DNS: отдельно сохраняются qname, resolver, A/AAAA, TTL, время, CNAME и признак происхождения. FakeIP и локальные/служебные адреса не становятся реальными IP кандидата. Negative answer, stale cache, TTL=0, смена набора/alias во время двух попыток отменяют предложение. Проверяется только конкретный IP с сохранением SNI/Host. Успех одного IP не разрешает остальные, семейство или подсеть. Разделяемые CDN-адреса нельзя безопасно распространить на другие домены: при невозможности доказать исходный scope применение IP-правила блокируется.

## Бюджет и состояния

Предлагаемые пределы: один job одновременно, очередь отсутствует; максимум 4 реальных адреса, 3 кандидата, 2 попытки на адрес/кандидат, 24 запроса и 60 секунд на job, timeout запроса до 2 секунд. Превышение бюджета даёт `inconclusive`. Порядок Zapret2 → Direct → WARP, недоступные/запрещённые этапы отмечаются как пропущенные. Отключённый Zapret2 не выдаётся за его отказ.

Идентичный job имеет cooldown 5 минут, глобально не более 12 jobs в час; явная отмена и disable останавливают будущие попытки. Фоновая проверка только opt-in, не чаще 5 минут, с теми же общими лимитами. Нет бесконечного recovery/retry и переключений selector ради теста.

Состояния: disabled → eligible → diagnosing → proposed → applied → rechecking → applied/rolled_back/expired. Несколько ошибок не запускают новый цикл сразу после rollback. Бюджет, cooldown и идентичность поколения не сбрасываются повторным RPC.

## Транзакция, хранение и откат

Предложение включает поколение UCI/runtime, исходную секцию, точные IP /32 или /128, исходный domain/source/port scope, выбранный профиль, доказательство, время проверки и expiry. TTL правила — не больше DNS TTL и 15 минут; для literal IP действует явный срок до 15 минут. При недостаточном scope применяется отказ, а не расширение правила.

До записи под существующей блокировкой перечитываются UCI и policy guard, повторно проверяются свежесть, ownership, конфликт и профиль WARP. Только server-generated proposal может применяться; клиентские поля `success`, IP и outbound не считаются доказательством. Произвольный payload не является разрешением создать Bypass.

Создание/обновление обычной managed-секции идёт через UCI API; WARP использует штатную модель tunnel. Валидируется новый конфиг, затем штатный apply. Сбой возвращает только собственную транзакцию; ручные изменения не перезаписываются. История ограничена 100 событиями, не содержит URI, ключей и тел ответов; записи flash только при изменении правила, не при каждом probe.

Откат удаляет/отключает только принадлежащий механизму и не изменённый вручную объект, возвращая исходную политику. При конфликте ownership — остановка и видимое сообщение. Disable прекращает автоподбор и убирает его активные исключения. Expiry, отрицательная повторная проверка, смена DNS/политики, потеря WARP и неизвестный clock после cold boot запрещают использование исключения. Проверка срока должна действовать при генерации/запуске и в runtime, а не только при открытом UI.

Общий JSON apply может закрывать TCP: ограничение №03 явно показывается перед включением применения. Успешный откат конфигурации не обещает восстановления закрытой сессии.

## Интерфейс и доступ

Во вкладке диагностики: назначение, порт, источник, «Проверка маршрута» и отдельный Dry-run. Рядом с результатом видны прогноз/наблюдение/проверка, запрещённые этапы и причины, DNS/FakeIP, IP, время и TTL. Отдельные элементы включают автоматику для конкретной секции/назначения, показывают предложение, историю, отключение и откат. Никакого применения от read-RPC. Write-RPC и ACL отделены от чтения; backend повторно проверяет ограничения независимо от UI.

## Единицы реализации после согласования

1. `diagnostics/route_policy.uc`: неизменяющий прогноз и guard; `tests/diagnostics/route_policy.test.uc` с таблицей приоритетов и неопределённостей.
2. `diagnostics/route_probe.uc`: единый ограниченный job и контракт transport; mock transport для негативных сценариев; production adapter допускает только путь с подтверждаемыми IP/outbound/TLS/HTTP. При нехватке API возможностей возвращает unsupported, не симулирует успех.
3. `diagnostics/route_auto.uc`: server-side proposals, блокировка, UCI ownership, сроки, apply/rollback и recheck; интеграция с validator/generator/lifecycle только в местах managed-правил. Проверки crash/restart/expired и конкурирующих изменений.
4. CLI/RPC/ACL и frontend diagnostic UI; отдельные типы и контракты диагностики и write actions. Целевые backend/frontend тесты, typecheck/build по затронутым точкам.

Точные сигнатуры и полный список файлов фиксируются в плане после согласования проекта и проверки transport API. Если core API не даёт необходимых доказательств, требуется отдельное минимальное расширение с локальным воспроизведением; существующий r10 не меняется ради обхода этой проверки.

## Проверки и передача

Сначала падающие синтетические тесты, затем код, затем свежие целевые прогоны в `--network none`. Матрица: protected endpoint и alias; false HTTP success; DNS temporary/negative/stale/rebinding; FakeIP; CDN/shared IP; A/AAAA mixed; duplicate IP; disabled WARP/Zapret2; Bypass/manual precedence; device/System/port scope; missing SRS; повтор RPC и cooldown; бюджет и cancel; TTL/reboot; конфликт UCI; ошибка apply/recheck и rollback. Отдельные spy-assertions доказывают отсутствие probe/mutation при запрете.

В TESTING записываются точные команды, свежие результаты и неудачные эксперименты. AI_HANDOFF/PROJECT_STATE отражают фактическую степень готовности, отдельно от старых зелёных №03. Проверяются актуальность DECISIONS, KNOWN_ISSUES, PITFALLS, ARCHITECTURE/COMPONENTS, ROADMAP и CHANGELOG; обновляются только затронутые. Аппаратная приёмка nft/PBR/реального egress/UI/reboot остаётся отдельным разрешённым этапом.

## Реализованное продолжение №04Б

Согласованный дизайн реализован отдельным patch 0006 поверх r10. Suppression уточнён: отдельный atomic JSON вместо записи в основной staged UCI. Exact-domain/IP/source lease после original matcher, two-attempt nonce contract, generation cancellation и finite budgets проверены локально. Подробный действующий контракт: [№04Б](../../AUTO_ROUTING_IMPLEMENTATION_04B.md); evidence — [TESTING](../../TESTING.md). ## Уточнение №04Б-ФИНАЛ — 2026-11-16

По явно разрешённому продолжению добавлен отдельный ordinary web mode (default пустой JSON) и сохранён legacy strict nonce. Web same-IP/hostname/path TLS+bounded GET получает healthy/suspected_failure/alternative_reachable, но никогда verified_for_apply или auto-apply. Только strict контракт может auto-apply. Manual eligibility server-side с прежними guards/TTL/проверенным source flow; IP-only только TCP diagnostic. Actual dial связывается с тем же core event, не с логом/соседним DNS. Web не перебирает A/AAAA. Lease требует единственный exact DestinationAddress original matcher; смешанный набор не pinning. Web recheck снимает lease и оставляет предложение. Полный контракт, false positives и аппаратные границы — [№04Б](../../AUTO_ROUTING_IMPLEMENTATION_04B.md), свежие доказательства — [TESTING](../../TESTING.md). Без universal-app/UDP/DPI/physical-egress обещаний.
