# Ограничение памяти журнала — план исправления

Цель: устранить подтверждённое синтетическим replay усиление расхода RAM при Info/Trace и открытии вкладки. Работает один ассистент, в текущем дереве, без установки/публикации и доступа к устройствам. Пользовательские r23/r24 изменения сохраняются.

Доказательство до изменения: `tests/service/log_journal_pressure.uc`, 16000 строк, 1620890 байт текста, 2040671 байт JSON, VmHWM 26776 kB (Linux x86_64, локальный контейнер). Это механизм риска, не установленная причина аппаратного OOM.

- [x] Регрессии: число записей, длинная UTF-8 строка, bounded restore, неизменившийся RPC, большой поток.
- [x] Journal: 256 КиБ текста, 2048 объектов, 512 КиБ JSON, 2048 байт на строку; кешировать размер записи, не сериализовать старые записи при каждом prune. Срок до 24h остаётся верхней границей, при заполнении вытеснять старые.
- [x] State: ограничить входной batch до выделения большого буфера, не собирать полный текст для unchanged, уменьшить RPC-страницу, освобождать снимок передачи после завершения/таймаута. Сохранять семантику clear и стабильной многостраничной передачи.
- [x] UI: показать фактический лимит; при готовом экспорте не менять поиск/уровни без решения пользователя.
- [x] Целевые ucode/frontend проверки, TypeScript/lint/build, docs gate; повторить replay, записать результат и ограничения.

Дополнение по прямому сообщению пользователя о мониторинге: ограничен исходный core-снимок до 200 последних non-DNS строк с реальным total; bounded heap вместо полного массива. UI сообщает о неполноте и не выдумывает закрытия. RPC ограничен по байтам, отображает причину отказа. Проверки и аппаратные границы — [LOGGING](../../LOGGING.md).

Самопроверка выполнена одним ассистентом согласно AGENTS, без review-субагента. На review добавлены regression release completed transfer, warning/discard legacy archive и invalidation browser cursor при обрезке restore. Внешние действия и аппаратный диагноз остаются вне выполненного scope.

Предложение по шуму обсуждается отдельно: группировать одинаковые события со счётчиком, сохранять исходные данные и значимые назначения/ошибки; не считать WAN недоступным по одному отказу VPN. Не добавлять дублирующий фильтр «Только ошибки». Изменение severity в core в это исправление не входит.
