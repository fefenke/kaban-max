Локальная работа 2026-11-15, без установки, публикации и полной финальной приёмки. Сохранены изменения №01 и прежний dirty tree. Закреплённый upstream commit не менялся. Новые patches 0003–0005 требуют **sing-box-kabanmax 1.14.4-r10**; опубликованный r9 не содержит этих защит. Backend minimum поднят вместе с `core/UPSTREAM`. Пакеты r10 здесь не собирались.

## Основное ТЗ

- `dnsmasq.domain` сохраняется; `local=/zone/` читается как option и list, включая несколько зон в одной записи. Явные `server=/zone/address` передаются локальному dnsmasq, который сам выполняет условную переадресацию. KABANMAX не создаёт отдельный транспорт к указанному адресу. `server=/zone/#`, обычные upstream-адреса без зоны и неподдерживаемые шаблоны не объявляются локальными зонами. Настройка dnsmasq, которая сама пересылает зону обратно в перехваченный resolver, по-прежнему ошибочна; произвольные пользовательские циклы автоматически не исправляются.
- Явные дополнительные зоны идут перед доменными правилами секций и IP-evaluate. Одноуровневые имена, стандартный DHCP-домен и PTR сохраняют локальный resolver. Поддерживается обычный синтаксис DNS-зон, включая `home.arpa` и reverse-зоны; IDN следует записывать в ASCII/Punycode.
- Исходящий трафик sing-box исключается по `NFT_OUTBOUND_MARK`, в том числе в сочетании с чужими битами. Системная DNS-цепочка больше не принимает любую ненулевую метку за исключение. В `priority_output_rules` проверяется только маска собственных routing-битов `0x1c000000`. Запись capture/held/FakeIP marks выполняет OR, не стирая чужие биты. Совпадение пространства битов двух служб требует отдельной настройки; OR не устраняет коллизии.
- `Only for Devices`: валидные IPv4/IPv6 и System сохраняют свои варианты inbound/source. Непустой невалидный список не создаёт unrestricted-правило. Пустой список `[]` означает существующий режим «без ограничения устройств»: отдельного флага «ограничение включено, но никто не выбран» в UCI нет. Пауза секции убирает её правила, а не создаёт глобальный DNS block. Frontend взаимного исключения двух device-списков не менялся.
- Различия системных и клиентских inbound, исключения устройств и порядок секций сохранены. Отдельный исторический crash-loop из Forkop 1.0.5 не воспроизведён: текущий core продолжает запуск, сохраняет валидный кэш и повторяет загрузку remote sets через выбранный detour. Скрытый Direct для загрузок не добавлялся.

## Смешанный DNS: почему потребовались три уровня защиты

1. Сам `match_response` раньше совпадал по любому IP и возвращал весь ответ. Для IP-Bypass generator теперь использует `response_address_all`: реальный ответ возвращается только если каждый адрес соответствует проверяемой ветке Bypass. Частичное совпадение выдаёт FakeIP. Если IP не совпали вообще, продолжаются нижние DNS-секции и штатный fallback. Доменный Bypass по-прежнему имеет свою обычную семантику и разрешает весь соответствующий домен.
2. Для FakeIP домен резолвится **в позиции IP-Bypass секции**, после более ранних секций и с её source/inbound-ограничениями. Это необходимый резолв для сопоставления IP, а не включение глобального предварительного резолва. Глобальные `disabled/all/selected` сохраняют порядок и область действия. Ошибка этого lookup останавливает соединение.
3. Core сопоставляет каждый resolved-кандидат с терминальным route/bypass-правилом и оставляет в dial-списке только совпавшие адреса. Приоритет принадлежит первой подходящей секции; отказ её dial не переводит оставшиеся адреса в Direct и не запускает нижнее правило. Имя назначения сохраняется для TLS/proxy. Это не параллельное соединение через несколько разных outbound: одна сессия использует кандидатов одного выбранного правила. Новая сессия сопоставляется заново.

Одного пункта 3 недостаточно: реальный IP из смешанного ответа мог пройти мимо nft, если защищающая его нижняя секция содержит только домен. Именно поэтому частичный DNS-hit сохраняет FakeIP, вместо выдачи клиенту всего реального RRset. Inline/SRS могут быть разными ветками одного Bypass; если весь ответ не покрывается одной response-веткой, консервативный FakeIP всё равно сохраняет правильное сопоставление в core.

| Сценарий | Локальное доказательство |
| --- | --- |
| Несколько A, частичный Bypass; обратный порядок RR | `TestKabanmaxGeneratedDNSMixedAnswers`: FakeIP; route regression оставляет только разрешённые Direct-кандидаты |
| A и AAAA, разные IPv4/IPv6 правила | Синтетический ответ с обоими типами, отдельные IPv6-проверки №01 и per-address route regression |
| Один IP из GeoIP/SRS; все IP совпали | Synthetic inline headless rules с теми же CIDR matcher-ами; частичный ответ FakeIP, полностью совпавший сохраняет реальный ответ |
| Ни одного Bypass IP или пустой address-ответ | Продолжение нижней FakeIP-секции; bootstrap не используется как fallback пользовательского DNS |
| Connection раньше Bypass и наоборот | Generated `priority/policy` fixtures: первая секция сохраняет приоритет |
| Повторный свежий ответ, изменение набора IP | Один DNS walker и router используются последовательно; новые RR/metadata сопоставляются заново, прежнее Direct-решение не переносится |
| FakeIP, `disabled/all/selected`, detour on/off, devices | Generated fixtures + реальный rule walker/resolve actions с synthetic Lookup; отдельные loopback DNS/SOCKS dialers |

DNS walker отключает DNS-кэш, чтобы каждый synthetic ответ действительно был новым. Это проверка отсутствия сохранённого **решения маршрута**, а не доказательство поведения всех TTL/optimistic/persistent cache после reboot на роутере. Возврат ещё валидного DNS-кэша сам по себе не является устаревшим решением маршрута.

Отдельный `TestKabanmaxGeneratedDNSMixedRealFakeIP` запускает настоящий Box/FakeIP transport/store и UDP DNS-inbound с локальным TCP DNS upstream: смешанный реальный ответ действительно превращается в адрес `198.18.0.0/16`. Это дополняет mock walker-проверки, но не проверяет kernel TPROXY/nft.

## Remote sets без первого валидного содержимого

Обнаружен отдельный fail-open: старт с пустым remote set не падал, но защищённый маршрут мог не совпасть и перейти в нижний Direct. Исправлены оба участка пути:

- В core неизвестный remote set консервативно удерживает свою секцию: если её source/port-ограничения подходят, маршрутизация возвращает `remote rule-set unavailable` вместо выбора outbound. Другие устройства не блокируются. После первого корректного содержимого обычное сопоставление восстанавливается без restart. Последний валидный набор при ошибке обновления сохраняется.
- В nft создаются `pending4/pending6` наборы. Пока нет полного валидного snapshot, потенциальный source/port scope секции передаётся в core даже для реальных адресов и Bypass. Provider-подсети и снятие pending применяются одной транзакцией. Доменные providers тоже участвуют в проверке готовности; валидный domain-only набор снимает guard, не выдумывая IP-подсети.
- Перед заменой core guards включаются заново, а worker синхронизируется с новым core. No-op Save не пересобирает таблицу. Явные исключения, локальные адреса и более ранние секции сохраняют свои приоритеты.

Если область такой секции — весь LAN и её первый набор недоступен, отказ может затронуть весь её неопределимый destination scope. Это сознательное fail-closed до загрузки/восстановления кэша, а не обещание определить неизвестные защищённые домены. Сервис и retry остаются работающими; незаметного разрешения Direct нет.
