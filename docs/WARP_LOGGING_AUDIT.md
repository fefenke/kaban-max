## Остальные проверенные требования

- Свежие пользовательские данные: `fallback_stable_user_evidence.go` требует нового TCP соединения, созданного во время текущего раунда, того же frozen leaf и положительного чтения. Старая сессия не должна отменять новый отказ. Но любые полученные байты не доказывают успешную прикладную операцию; межсервисное veto требует отдельного regression сценария.
- Периодические проверки: stable loop учитывает idle timeout и активность новых Dial/ListenPacket. Одни долгоживущие соединения не обновляют lastActive каждым пакетом. Возможная задержка обнаружения на таком трафике — статический риск, не установленная причина текущего сбоя.
- Автоприменение не было выключено: после mixed проверки и cooldown IP самостоятельно применился all_devices/all_ports. Подтверждён конфликт бюджетов: web attempt5s при fallback attempt8s; две независимые подтверждённые попытки обязательны. Это может давать неубедительный результат, но одна TCP доступность не должна становиться основанием Apply. [Наблюдения](AUTO_ROUTING_AUTO_APPLY_DELAY.md).
- Успешный Pending результат сохраняется: `successfulCheckLocked` возвращает retained proposed decision; Sweep не запускает его заново только по таймеру. Неуспешный результат и новый source failure могут привести к новой попытке. Час в счётчике одинаковых failures не равен часу хранения записи.
- Persistent Applied IP исключён из срока временных leases через `!PersistentIP`. Границы RAM и пользовательское удаление остаются; обещания бесконечного хранения при исчерпании памяти нет.
- Порт: `diagnostics/warp_ports.uc` имеет отдельный ключ секция+профиль, boot quota в `/var/run`, проверку instance/порта и600s, приватный UCI cursor; совпавший hint закрывает окно без flash commit. Поздние изменения остаются RAM-only. Подтверждение основано на WG handshake/data, не на десятиминутном успешном YouTube; полный reboot soak этим аудитом не выполнен.
- Журнал: `service/log_journal.uc` ограничивает возраст24h, размер256KiB,2048 записей, строку2048байт; раннее вытеснение при заполнении возможно. `state_service.collect_logs` не вводит отдельного скрытия WARP по severity: он собирает ограниченный logread tail. Отфильтрованное ядром сообщение journal восстановить не может.
- WAN: при чтении кольцевого logread событий WAN не найдено. Это не доказывает, что gate никогда не включался: старые сообщения могли быть вытеснены. Нельзя объявлять именно WAN gate причиной текущей тишины.
- Инструкция UPDATE_023 содержит прежний вложенный SSH launcher, который в пользовательском Windows запуске не создал процесс/лог. Это отдельная ошибка процедуры обновления, не объяснение runtime WARP. Установка на остальные устройства в аудите не запускалась.

## Что требуется проверять при исправлении

1. Сохранить lifecycle scope уходящего поколения. Разделить routine завершение потока и значимый runtime отказ; не включать глобальный Debug ради обхода дефекта.
2. Добавить ограниченные Warn для изменения состояния активного fallback и ошибок применённого маршрута. WAN gate и его тесты сохранить по прямому уточнению пользователя; подавление при подтверждённом WAN outage намеренное.
3. Не стирать primary-failed/confirmation-passed. Сравнивать тот же контрольный сервис на активном и резерве с повторным bounded подтверждением. Общий отказ сервиса на обоих не должен вызывать бесконечное переключение.
4. Проверить реальные TCP+TLS+HTTP данные, оба профиля, полный и частичный отказ, оба сломаны, восстановление приоритета, долгоживущие потоки, новые/старые пользовательские соединения, параллельный autorouting и ограничение повторов. Только затем согласованный reload/reboot и установка.

Эти пункты не реализованы в рамках анализа. Ошибки нельзя считать устранёнными на основании прежних зелёных тестов: часть тестов закрепляла нежелательную политику, а частичный отказ контрольных сервисов не покрывалась аппаратной приёмкой.
